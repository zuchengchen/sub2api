# Chat Completions 原生推理状态续接

这项功能让已有 Chat Completions 客户端在工具调用和后续普通用户轮次中复用上游原生 Responses 输出项。服务器在转换前保留完整的原生状态，并将它与客户端真正收到的 assistant 消息及当时实际发送的输入前缀绑定。

功能默认关闭。初期适用范围为 OpenAI OAuth 的 Chat Completions → Codex Responses 路径；API Key、PAT、Agent Identity、第三方传输插件与其他平台保持原路径。缺少明确会话标识、无法建立可信凭据身份、未知输出类型、没有可定位的可见 assistant 片段或未完成响应时不建立可恢复记录。支持完整工具回合，以及已有文本转换支持的 assistant 消息回合。

原生 Codex OAuth 的 Responses / WS→HTTP 路径同时保留固定 Codex 的 `prefix_suffix` 项 ID、reasoning 内容的原生形式及原始工具配对。公开 API Key 上游继续使用原有兼容规则。WS→HTTP 重建历史时，缺失的 reasoning content 按固定源码序列化为 `null`；compaction 通过历史替换续接，不补写普通输出的轮次元数据。

## 固定源码构建的 TLS 配置

本轮固定 Codex GNU 源码构建使用 OpenSSL 3.5.5；旧 `openssl36` 档仍代表此前校准的发布包，不应通过修改同名模板混用两种来源。需要匹配本轮 GNU 构建时，显式设置进程环境变量 `SUB2API_CODEX_NATIVE_TLS_PROFILE=openssl35-gnu`。该选择由 Codex 业务 HTTP 与认证 HTTP 共用；自定义 CA 的 HTTP 仍使用 `rustls-h2`，WS 仍使用 `rustls`。账号显式 TLS 配置保持优先。

空值或 `openssl36` 保留既有默认；其他值在应用配置验证时拒绝启动。新档携带实际支持的 zlib / zstd 证书压缩扩展，继续验证证书。该配置不由客户端请求头选择，也不根据宿主库版本自动猜测。修改后需重启服务；回滚时恢复此前环境配置。精确协议验收应记录所选档位和固定参考来源。

请求独占的 H2 连接仅在底层响应已正常结束、请求也完整发送且无错误或取消时正常退役。如果已解析的最后一帧尚未完成本地交付，或请求最后一帧的发送完成状态尚未发布，会有界等待现有完成信号和写锁后复查，两种等待共用 250 ms；随后发送 GOAWAY 的既有退役阶段另有 250 ms 预算，因此这两个关闭阶段最坏约 500 ms。解压器 EOF、Content-Length、未完成发送或仅获取写锁都不能冒充完整传输；超时仍中止连接，不重发请求。

## 运行开关

通过后端 `settings` 的 `openai_native_reasoning_replay_config` 配置，仅由管理员控制：

```json
{"mode":"observe","user_ids":[428]}
```

模式：

- `off`：不保存或恢复状态。
- `observe`：观察真实请求并保存符合条件的完整状态，发给上游的请求保持原兼容转换结果。
- `replay`：严格匹配成功时恢复状态，并保存新的完整结果。

空用户列表不表示所有用户。可添加 RFC3339 格式的 `expires_at`；到期后关闭。设置缺失、非法或读取失败均回退关闭。设置缓存最多 5 秒，修改对随后请求生效；已开始的请求沿用其开始时确定的模式。

### 全站 GPT 对话模型

在运行**支持本字段的版本**后，给现有配置增加 `"all_users_gpt_models": true` 并使用 `replay` 模式，即可覆盖现有和以后注册的用户。以下是只启用此范围的最小配置。有既有名单或到期时间的站点应合并字段，保留原值。

```json
{"mode":"replay","all_users_gpt_models":true}
```

网关按最终发给 OpenAI 的 GPT 对话模型判断，覆盖 GPT-4o、GPT-5、GPT-6 的文本模型变体和内置官方目录里的具名 GPT 对话模型。映射到其他模型、图像生成、实时音频和转录走各自的协议。授权覆盖全站时，每次恢复仍绑定用户、API Key、会话、线程、实际上游模型和上游凭据。对于已经开启的 GPT-6.1 Sol 和 GPT-6.2 会话，继续使用各自已有的记录格式。

只发 `messages` 的 Chat 客户端也可以使用提示缓存。在支持该字段的 OpenAI 上游，网关从开头的指令、工具和首条用户消息派生稳定的缓存路由键。客户端也可以用会话头指定对话，同时用单独的 `prompt_cache_key` 指定可复用前缀。原生推理状态另需可验证的会话标识和完全匹配的历史。首次请求、前缀变化和上游缓存到期均会影响实际的 `cached_tokens`。[OpenAI 提示缓存说明](https://developers.openai.com/api/docs/guides/prompt-caching)

在 Chat 转 Codex Responses 时，追加的系统指令会以 `developer` 消息留在原位置。网关进行时区换算时使用消息自带的日期、时钟和源时区。无法确定唯一时刻的历史保留客户端原文。使用完整消息数组的 GPT Responses 客户端即使在后续轮次追加系统或开发者指令，也能继续沿用首轮的账号路由。对于没有显式会话标识的原生 Responses 请求，字符串和消息数组仍按各自的历史规则选择账号，从一种格式切换到另一种时可能需要重新预热。

移除 `all_users_gpt_models` 或改为 `false` 可撤回这项全站授权，其他已有范围按原配置执行。回滚到早期二进制前先还原此前保存的完整配置，旧版本会拒绝不认识的字段。

生产设置已经处于 `replay` 时，可以在发版后用一条更新合并新字段。先保存原配置以便回退，并确认到期时间覆盖计划的启用时段。

```sql
UPDATE settings
SET value = (value::jsonb || '{"all_users_gpt_models":true}'::jsonb)::text, updated_at = NOW()
WHERE key = 'openai_native_reasoning_replay_config' AND value::jsonb->>'mode' = 'replay';
```

### 按用户或单一模型授权

按模型选择用户时，可以在已有配置中添加目标模型的名单。例如，保留用户 428 的旧授权，给用户 358 开启 `gpt-6.1-sol`。

```json
{"mode":"replay","user_ids":[428],"model_user_ids":{"gpt-6.1-sol":[358]}}
```

`model_user_ids` 接受 `gpt-6.1-sol`、`gpt-6.2-sol` 和 `gpt-6.2-astra` 三个精确模型名。每个模型独立限制为最多 256 个正整数用户 ID，按输入列表长度检查上限，再排序去重。空列表授权零位用户。非法键、非法 ID、超限列表或重复 JSON 成员会关闭整个设置。

例如，已有配置同时包含上述名单和 6.1 的全用户授权时，给用户 358 增加两款 6.2 模型后，配置如下。操作时应合并到先前读取的完整配置，并保留其中的其他用户、模式和到期时间。

```json
{"mode":"replay","user_ids":[428],"all_users_models":["gpt-6.1-sol"],"model_user_ids":{"gpt-6.1-sol":[358],"gpt-6.2-sol":[358],"gpt-6.2-astra":[358]}}
```

用户同时列在 `user_ids` 与某款 6.2 的模型名单时，该模型走按模型授权的严格续接规则，该用户其他模型继续按各自授权处理。对于 `gpt-6.1-sol`，先检查 `user_ids`，再检查该模型名单和 `all_users_models`。

目标模型需要向所有现有和后续用户开放时，显式添加模型作用域：

```json
{"mode":"replay","user_ids":[428],"all_users_models":["gpt-6.1-sol"]}
```

`all_users_models` 目前只接受一个精确模型名 `gpt-6.1-sol`；空列表不开放任何额外用户，其他模型、通配符、重复项和非法配置均关闭。授权按账号映射及规范化后的实际上游模型判断，并在最终出站请求准备时再次核对。`user_ids` 保留原有模型范围，因此上例中的用户 428 继续使用原有规则，其他用户只在目标模型的适用协议路径开启。会话、用户/Key、上游凭据、完整状态及资源上限仍是独立条件；模型授权不代表每次都能恢复。

`mode` 和 `expires_at` 约束所有授权范围。未开全站 GPT 授权时，从对应模型名单中移除用户即可撤回该用户的 6.2 灰度。若该用户也在 `user_ids`，该模型随即回到旧授权路径。回滚二进制前恢复先前保存的设置，旧版本会拒绝含 6.2 模型键的配置。移除 `all_users_models` 可撤回 6.1 的全用户授权，`mode: off` 可关闭全部续接。

例如，先读取并保存原值，再在经过授权的数据库会话中启用单用户观察：

```sql
SELECT value FROM settings WHERE key = 'openai_native_reasoning_replay_config';
INSERT INTO settings (key, value, updated_at)
VALUES ('openai_native_reasoning_replay_config', '{"mode":"observe","user_ids":[428]}', NOW())
ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value, updated_at = NOW();
```

经过功能验证后将模式改为 `replay`。回退时将模式设为 `off`，或恢复上线前保存的原值。不清空生产 Redis，不修改用户 Key、余额或上游账号设置。

## 存储与边界

缓存使用独立 Redis 命名空间，与现有反方向桥接的推理文本缓存分离。完整原生输出使用现有 AES-GCM 实现、以应用 JWT 密钥派生的独立用途密钥保护；上游 `encrypted_content` 本身始终保持不透明。应用密钥变化导致旧记录无法读取时安全回退，不尝试破解或迁移旧状态。

默认存储预算也可以通过 `gateway.native_reasoning_replay` 的对应项缩小：

| 配置项 | 默认值及硬上限 |
| --- | --- |
| `ttl_seconds` | 3600 |
| `io_timeout_ms` | 100 |
| `max_entry_bytes` | 262144，包含存储摘要头和应用密文 |
| `max_entries_per_user` | 64 |
| `max_entries_global` | 1024 |
| `max_lookups` | 每请求 32 |
| `max_history_bytes` | 4194304 |
| `max_output_items` | 128 |

零值采用默认值；负数或超过硬上限的配置拒绝加载。有效 payload 上限约为每用户 16 MiB、全局 256 MiB，另有有界 Redis 元数据。相同输出的重复提交不延长 TTL。这是本地续接状态的保留时间，并不控制上游提示词缓存寿命。

每个记录绑定用户、API Key、显式会话、实际模型、可信上游凭据身份、原始及最终语义参数、工具名映射、完整可见历史和生成时的实际原生输入前缀。只按规范化后的模型名或 session_id 匹配是不够的。

网关在转发前验证历史并计算实际出站 `input` 的摘要。收到完整响应后，网关在已验证的历史摘要上追加实际交付的 assistant 消息，再写入缓存。这样长对话只需在写入时处理本轮新增的内容，保留已有的缓存键格式和最多 100 毫秒的写入时限。

采用按模型续接的 Chat 请求绑定显式会话和线程，并把兼容会话头及 `client_metadata` 内的身份传递给 Codex HTTP 请求。按请求体内嵌的 turn metadata、请求体平面 metadata、头内 turn metadata、单独身份头的优先级解析。会话身份来自这些显式标识，`prompt_cache_key` 仍用于缓存路由。不同线程和实际上游模型各自保存可恢复的历史。缺少有效身份，或只有父线程而无法识别子会话时，请求按原兼容路径转发。

恢复发生在请求构造和语义规范化完成之后；完整原生数组不再经过工具名或 ID 的二次改写。工具结果的调用 ID 和类型同时配对还原。没有工具调用的 assistant 回合则要求完整转换片段与前后锚点唯一匹配；重复结构存在多个匹配位置时不恢复，也不把工具输出冒充普通消息绕过配对。每一组的祖先原生前缀都必须一致：缓存逐出、历史编辑、压缩、并行分支、参数变化或换凭据不能通过拼接不兼容的后代状态来补救。

恢复能力是有界优化。无法证明匹配、历史或输出过大、结果缺失、存储不可用等情况保持原兼容路径。上线前丢失的推理状态无法补回。网关自有的固定工具能力说明与基础提示保持稳定，不随新用户轮次改写历史；请求自身仍使用新的轮次身份。显式权限、环境或其他语义前缀变化仍可能产生保守的缓存未命中。

客户端立即续接时，同进程内已登记且作用域、参数和历史前缀严格匹配的上一轮发布会先等待完成；等待与随后的缓存读取共用 100 ms I/O 预算。登记上限为每用户 64 个不同历史前缀、全局 1024 个；超限或等待超时安全回退。其他进程没有相应登记时不会等待，尚未发布的记录仍按缓存未命中处理。

## 完成、错误与重试

原生捕获以完整、可验证的 Responses 终态为逻辑边界，与固定 Codex 的消费者一致，不依赖 TCP EOF 或其后的可选 `[DONE]` 预读字节。客户端 Chat 捕获则必须确认实际写成功的响应：流式需要完整 `finish_reason` 和 `[DONE]`；非流式需要完整唯一 assistant。完整交付确认前的取消、短写、冲突、错误和不完整终态不提交缓存。仅当这些检查通过且转发与客户端 context 均仍有效时，已登记的发布才转入独立的最多 100 ms 提交窗口；随后客户端关闭已完成响应不会取消这次缓存写入，超时和正常返回都会释放登记。

目标模型的流式 `replay` 在底层完整写入 finish 和 `[DONE]` 后、最后一次 Flush 前接管该提交窗口。这样客户端在看到 `[DONE]` 后立即关闭也不会撤销已确认的发布。真正的缓存提交仍在转发结束后再次检查完整结果、凭据和交付状态；不会在写回调中提交，也不会为 Flush 或缓存写入重新延长预算。其他模型、观察模式及非流式路径保持原有时序。成功的服务端写入不等同于远端客户端已读取的确认。

若成功终态的 `output` 缺失或为 `[]`，仅在同一完整事件流已有可信响应身份、所有声明的输出索引从 0 连续、每个 added 都由身份一致的完整 done 闭合、done 首次到达顺序与索引一致时，才用已收到的完整 done 项构造内部校验结果。所有已观察输出引用必须指向同一对应项；未知事件、冲突、断流、错误、缺项、显式 `output: null` 或缺少明确 completed 状态均不能走此路径。仍须存在已支持的工具调用或可见 assistant 消息，并与客户端实际收到的 assistant 精确匹配。本轮没有新增密文的纯工具输出也完整保存，保留其原生 ID、命名空间及扩展字段；不会借此生成密文，也不要求先前已命中另一条缓存。存在事件序号时要求全流一致且连续，完全无序号的合法流仍可按以上条件验证。非空终态数组继续使用原有逐项精确校验。该过程保留 done 项及终态的未知字段，不生成 ID、phase、工具参数或密文，也不修改实际转发的响应。它证明的是这条完整事件流已声明的输出集合，不宣称恢复上游从未发送的隐藏内容。

上游返回完整 HTTP 400，且结构化 `error.code` 精确为 `invalid_encrypted_content` 时，对本次实际恢复的记录作失效处理。即使队列心跳已提交响应、客户端已取消，或错误携带用量/部分输出，也不能继续复用已确认遭到拒绝的状态。只有没有用量或部分输出、客户端尚未写出且未取消时，才允许至多重试一次原兼容请求。第二次失败按原错误处理。已写出的 SSE 请求不自动重放；明确的加密状态拒绝仅影响后续恢复。

失效写入失败时，进程内有界拒绝屏障阻止再次注入同一摘要。屏障容量耗尽时，在其保护窗口内回退原兼容路径。跨进程或重启后的持久拒绝仍依赖 Redis 写入成功；所有记录都有短 TTL。

内部 OAuth 401 恢复若改变实际授权主体，发送前阻止携带旧缓存状态的请求并安全回退。仅过期时间变化且主体不变的令牌刷新不必丢失状态。成功响应的授权主体与本次绑定不一致时不提交新记录。

## 验证与观测

协议正确性通过真实生产转换路径、本地 HTTP/SSE 双端记录、完整原生项对比、多用户隔离、Redis 集成和并发检查验证。单独的文本缓存或辅助函数测试不能替代这些检查。

在同一用户、API Key、实际上游模型、上游账号和会话内，比较上下文规模与请求间隔相近的连续 Chat 请求。分别报告每条会话的首轮和续接轮。按 `100.0 * SUM(cache_read_tokens) / NULLIF(SUM(input_tokens + cache_creation_tokens + cache_read_tokens), 0)` 计算输入 token 的加权命中百分比，再核对上游原始用量、`restored_groups`、费用和延迟。采样字段和完整交付的判断方法见[单用户缓存诊断](user-cache-diagnostics.md)。

GPT Image 需按图像接口单独核对。对于官方 GPT-Image-2 和 GPT-Image-2.5，缓存输入定价适用于 Responses 的图像生成工具，入口为直接 Images API 时按其自身价格计算。官方 Responses 用量不列出这些图像缓存 token。兼容上游若提供图像工具自己的缓存明细，按该工具实际报告记录。主对话模型的缓存读取量属于主模型。[OpenAI 图像用量说明](https://developers.openai.com/api/docs/guides/image-generation#cached-input-pricing)

生产采用正式 `czc-*` 标签与 GitHub Release 部署，按 AGENTS.md 重建前端并执行 embed 构建。上线后按模型和入站协议比较同规模对话的后续轮次。需要回退时，恢复之前保存的完整开关配置，必要时恢复已校验的旧标签备份，并重新检查版本、首页及 origin 发布链接。
