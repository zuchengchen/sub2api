## 错误码含义与处理方案

先同时查看 **HTTP 状态、错误文字和请求是否真正完成**。不同入口的错误格式不完全相同：

```json
{
  "code": "API_KEY_EXPIRED",
  "message": "API key 已过期"
}
```

上面是站点验证阶段可能返回的格式。进入网关后，客户端也可能收到下面这种格式：

```json
{
  "error": {
    "type": "rate_limit_exceeded",
    "message": "请求过于频繁，请稍后重试"
  }
}
```

这两段用于说明结构，不代表每个客户端都会显示相同字段或原样文字。大写代号可能只出现在某些入口或记录里；不能仅凭没看到代号就排除该原因。

### 先看三位数

| 状态码 | 常见含义 | 先做什么 |
| --- | --- | --- |
| `200` | HTTP 请求已被接受或成功返回 | 检查正文；流式请求还要看最终完成或失败事件 |
| `400` | 请求内容、参数或认证方式有误 | 核对模型、参数；不要把 Key 放到网址查询参数中 |
| `401` | Key 缺失、无效、停用，或用户被停用 | 核对 Key 和用户状态，避免反复提交错误凭据 |
| `403` | Key 过期、余额不足、IP/分组权限或订阅条件不满足等 | 按具体错误检查[控制台](/dashboard)、Key 状态及分组 |
| `404` | 地址、模型或资源不存在 | 核对完整请求路径和模型名，不能一律靠添加 `/v1` 解决 |
| `409` | 当前操作与现有状态冲突，例如兑换码已经使用 | 先检查记录和当前状态，不要盲目重复提交 |
| `413` | 请求内容太大 | 缩短内容或减少一次发送的文件 |
| `429` | 请求频率、并发或消费额度受限 | 区分短期限流与额度耗尽，见下表 |
| `499` | 客户端断开、取消或网络中断等 | 先检查结果和用量；已处理的请求仍可能计费 |
| `500` | 服务内部异常 | 稍后有限次数重试，持续出现则联系管理员 |
| `502` | 网关或上游请求未成功 | 查看具体错误，不能据此断定本站其他部分一定正常 |
| `503` | 资源或计费等服务暂不可用 | 等待并检查错误文字，避免连续快速请求 |
| `504` | 等待上游超时 | 先核对已有结果和用量，再决定是否重试 |

超时、取消或 HTTP 200 的流中出现失败事件，都不能单独证明“没有产生费用”。

### 再看具体原因代号

下列代号用于帮助定位；部分网关会把它们转换为小写分类和错误文字，不一定原样返回。

| 代号或场景 | 含义与处理 |
| --- | --- |
| `INSUFFICIENT_BALANCE` | 钱包余额不足，常见为 403；核对余额后按需购买余额兑换码 |
| `API_KEY_EXPIRED` | Key 已过期，403；在 Key 管理页处理有效期或创建新 Key |
| `API_KEY_QUOTA_EXHAUSTED` / `insufficient_quota` | Key 总额度用尽，429；Responses 入口可能使用后者作为 type/code，等待下一分钟不会自动补足总额度 |
| `API_KEY_RATE_5H_EXCEEDED` | Key 的 5 小时消费窗口额度用尽，429 |
| `API_KEY_RATE_1D_EXCEEDED` | Key 的 24 小时消费窗口额度用尽，429 |
| `API_KEY_RATE_7D_EXCEEDED` | Key 的 7 天消费窗口额度用尽，429 |
| `USER_RPM_EXCEEDED` | 用户每分钟请求上限，429；减少并发和频率 |
| `GROUP_RPM_EXCEEDED` | 当前用户在该分组内的每分钟请求上限，429；不是整个分组是否繁忙的判断 |
| `USER_PLATFORM_DAILY_QUOTA_EXHAUSTED` | 当前用户在该平台的日额度用尽，429 |
| `USER_PLATFORM_WEEKLY_QUOTA_EXHAUSTED` | 当前用户在该平台的周额度用尽，429 |
| `USER_PLATFORM_MONTHLY_QUOTA_EXHAUSTED` | 当前用户在该平台的 30 天窗口额度用尽，429，不一定是自然月 |
| `SUBSCRIPTION_NOT_FOUND` / `SUBSCRIPTION_INVALID` | 订阅不存在、无效或已过期等，403；检查所选分组和订阅状态 |
| `USAGE_LIMIT_EXCEEDED` | 订阅的用量限额已达到，可能返回 429；按对应窗口处理 |
| `BILLING_SERVICE_ERROR` / `billing_service_error` | 计费服务暂不可用，网关可能返回 503 和小写类型；稍后重试 |

Key 的 5 小时、24 小时、7 天窗口应以 Key 页面或用量查询显示的重置倒计时为准，不能保证按你的本地零点重置。用户平台日/周额度按服务端时区计算，当前为 `Asia/Shanghai`；日窗口到次日零点、周窗口到下周一零点，月额度使用 30 天窗口。订阅另有自己的窗口，不能混用这些时间规则。

换 Key 不会消除用户、分组对该用户或平台级别的限制。给钱包充值也不等于重置 Key 总额度、窗口额度或订阅限额。

### 最后看分类名

| `error.type` 分类 | 常见处理方向 |
| --- | --- |
| `authentication_error` | 检查 Key 与用户状态 |
| `permission_error` | 检查 IP、分组和模型权限 |
| `billing_error` | 检查余额或计费资格 |
| `invalid_request_error` | 检查请求参数、模型及内容大小 |
| `not_found_error` | 检查地址和资源是否存在 |
| `insufficient_quota` | 检查 Key 总额度等消费限制 |
| `rate_limit_exceeded` / `rate_limit_error` | 结合文字区分频率、并发、排队或消费窗口限额 |
| `upstream_error` / `provider_error` | 查看上游失败原因，有限次数重试 |
| `api_error` / `server_error` | 服务错误持续出现时联系管理员 |
| `overloaded_error` | 降低并发并等待资源恢复 |
| `billing_service_error` | 等待计费服务恢复 |

### 关于自动重试

如果响应带 `Retry-After`，至少等待指定时间；本站相关限流响应使用秒数。没有提示时逐步延长间隔，并限制重试次数。不同客户端是否自动遵循该提示，需要检查其实际行为。

余额、权限、过期或总额度问题先处理原因，连续重发不会解决。中断或超时后先查看已有结果与[用量记录](/usage)，再决定是否重试，避免重复任务和费用。
