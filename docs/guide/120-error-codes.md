## 错误码含义与处理方案

出错时，屏幕上一般会出现三种线索。看懂任意一种就够了：

- **一个三位数**，例如 `401`、`429`。它叫“状态码”，用来说明问题大概出在哪一层。
- **一串大写英文加下划线**，例如 `INSUFFICIENT_BALANCE`。本教程叫它“具体原因代号”，它比三位数更精确。
- **一个小写英文单词组合**，例如 `rate_limit_exceeded`。它是错误的“分类名”，出现在 `type` 位置。

完整的错误内容通常长这样，三种线索经常同时出现：

```json
{
  "error": {
    "type": "rate_limit_exceeded",
    "message": "user requests-per-minute limit exceeded"
  }
}
```

不需要背这些代号。看到问题时回到本节查表即可。

### 先看三位数

| 三位数 | 大概意思 | 先做什么 |
| --- | --- | --- |
| `200` | 成功 | 不用处理 |
| `400` | 请求内容本身有问题，通常是模型名或参数填错 | 检查模型名称是否和[模型广场](/model-plaza)一致 |
| `401` | 没有通过身份验证，几乎都是 API Key 的问题 | 重新复制 API Key，删掉前后空格，然后重启 Codex |
| `403` | 身份没问题，但这次不允许，可能是余额不足或没有该模型权限 | 先看[控制台](/usage)的“可用余额”，再确认分组是否包含这个模型 |
| `404` | 地址或资源不存在 | 重点检查服务地址结尾有没有 `/v1` |
| `409` | 和已有数据冲突，例如名称重复 | 按页面提示换一个名称再提交 |
| `413` | 发送的内容太大 | 缩短对话或减少一次发送的文件，然后重试 |
| `429` | 太频繁，或某个限额已经用完 | 等一会儿再试；反复出现时查限额和余额，见下面两张表 |
| `499` | 请求被自己这边中断了，例如提前按了 Ctrl+C 或关掉窗口 | 属于正常现象，重新发送即可 |
| `500` | 本站内部出错 | 稍后重试；持续出现时联系管理员 |
| `502` | 本站正常，但上游模型服务这次没成功 | 稍后重试，或换一个模型再试 |
| `503` | 暂时没有可用的服务资源 | 等几分钟再试，不要连续快速重试 |
| `504` | 上游响应太慢，超时了 | 缩短请求内容后重试，或换一个模型 |

`400` 到 `499` 通常是这次请求或账户状态的问题，改一下就能解决；`500` 及以上一般不是你的操作造成的，等待或重试更有效。

### 再看具体原因代号

这些代号出现在错误文字里，比三位数更能说明该做什么。

| 代号 | 含义 | 处理方案 |
| --- | --- | --- |
| `INSUFFICIENT_BALANCE` | 可用余额不够（返回 `403`） | 打开[购买兑换码](/redeem-store)买一张，再到[兑换余额](/redeem)兑换 |
| `API_KEY_EXPIRED` | 这个 API Key 已过期（返回 `403`） | 到[API Key 管理](/keys)新建一个，并更新 Codex 配置 |
| `API_KEY_QUOTA_EXHAUSTED` | 这个 Key 自己设的额度用完了（返回 `429`） | 在 API Key 管理里调高额度，或换一个 Key |
| `API_KEY_RATE_5H_EXCEEDED` | 这个 Key 的 5 小时限额用完了（返回 `429`） | 等限额窗口过去，或换一个 Key |
| `API_KEY_RATE_1D_EXCEEDED` | 这个 Key 的一天限额用完了（返回 `429`） | 等第二天，或换一个 Key |
| `API_KEY_RATE_7D_EXCEEDED` | 这个 Key 的 7 天限额用完了（返回 `429`） | 等限额窗口过去，或换一个 Key |
| `USER_RPM_EXCEEDED` | 你这一分钟发的请求太多了（返回 `429`） | 等下一分钟；把并行任务数量调小 |
| `GROUP_RPM_EXCEEDED` | 当前分组这一分钟太忙了（返回 `429`） | 稍等重试，或换一个分组 |
| `USER_PLATFORM_DAILY_QUOTA_EXHAUSTED` | 今天在这个平台的用量额度用完了（返回 `429`） | 等额度重置；错误信息里通常会带重置时间 |
| `USER_PLATFORM_WEEKLY_QUOTA_EXHAUSTED` | 本周额度用完了（返回 `429`） | 同上，等窗口重置 |
| `USER_PLATFORM_MONTHLY_QUOTA_EXHAUSTED` | 本月额度用完了（返回 `429`） | 同上，等窗口重置 |
| `SUBSCRIPTION_INVALID` | 订阅无效或已过期（返回 `403`） | 确认订阅状态，或改用余额计费的分组 |
| `BILLING_SERVICE_ERROR` | 计费服务暂时不可用（返回 `503`） | 这不是你的问题，稍后重试即可 |

看到 `429` 时先分清是哪一种：**限额用完**要等窗口重置，**发得太快**只要放慢速度就能马上恢复。

### 最后看分类名

有些客户端只显示 `type` 这个分类名。对照如下：

| 分类名 | 说明 | 处理方向 |
| --- | --- | --- |
| `authentication_error` | 身份验证失败 | 检查 API Key |
| `permission_error` | 没有这次操作的权限 | 检查分组和模型权限 |
| `billing_error` | 余额或计费相关 | 检查可用余额 |
| `invalid_request_error` | 请求内容有问题 | 检查模型名、参数和请求大小 |
| `not_found_error` | 找不到对应资源 | 检查服务地址和模型名 |
| `rate_limit_exceeded` | 触发了限流或限额 | 等待后重试，见上面的代号表 |
| `rate_limit_error` | 同样表示被限流，多为并发或排队已满 | 减少同时进行的请求数量 |
| `upstream_error` / `provider_error` | 上游模型服务出错 | 稍后重试或换模型 |
| `api_error` / `server_error` | 服务端错误 | 稍后重试；持续出现时联系管理员 |
| `overloaded_error` | 服务当前过载 | 等几分钟再试 |

`rate_limit_exceeded` 和 `rate_limit_error` 两种写法都表示“被限流了”，处理方式一样：先放慢，再看是不是限额用完。

### 关于自动重试

被限流时，返回内容里可能带一个叫 `Retry-After` 的数字，单位是秒，表示建议等待多久。大部分客户端会自动按它退避重试，通常不需要手工处理。

如果自己写脚本调用，建议看到 `429` 时按这个数字等待，而不是立刻重试。连续快速重试只会让限额恢复得更慢。
